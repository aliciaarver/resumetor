# Коммиты — правила нейминга

Полная версия. Компактную (её загружает Claude при работе над задачей) см. в `rules/compact/commits.md`. Здесь — то же самое чуть подробнее, для человека.

## Ветка

Куда коммитить зависит от того, из-за чего была правка.

- **Задача из трекера** — запуск через кнопку «Работать над задачей» в дашборде. `writeCode` сам переключает Claude на ветку с именем = ID задачи (`PROJ-142` для YouTrack, shortLink для Trello). Все коммиты и пуш по этой задаче идут на эту ветку, туда же в конце деплоится move в «На тестировании».
- **Правки без задачи** — рефакторинг, улучшения самого дашборда, мелкие фиксы, которые разработчик просит напрямую (в чате, а не через карточку трекера). Коммит и пуш идут **прямо в `main`** (или как называется основная ветка у проекта — проверь `git symbolic-ref refs/remotes/origin/HEAD`). Никаких `feature/…` или `chore/…` веток под такие правки не создавай.
- `git push --force` (или `--force-with-lease`) на `main`/`master` — никогда, без отдельной явной просьбы.
- Если не уверен, куда коммитить — спроси, не гадай.

## Формат сообщения

```
<тип>(<ID задачи>): <краткое описание>
```

### Тип (обязательно)

| Тип        | Когда использовать                                                                |
| ---------- | --------------------------------------------------------------------------------- |
| `feat`     | Новая функциональность — новая кнопка, роут, эндпоинт, поле в ответе              |
| `fix`      | Исправление бага — баг был виден пользователю или ломал сборку/тесты              |
| `refactor` | Изменение кода без изменения поведения — переименования, вынос функций, упрощение |
| `style`    | Whitespace, форматирование, CSS без логики                                        |
| `docs`     | Правки документации — CLAUDE.md, README.md, TECH-LEAD.md, PM.md, rules/           |
| `test`     | Добавление или правка тестов                                                      |
| `chore`    | Конфиги, зависимости, скрипты сборки, .env, .gitignore                            |
| `perf`     | Оптимизация производительности — с замером до/после в теле, если не тривиально    |

Если сомневаешься между `feat` и `fix` — смотри, была ли раньше эта функциональность. Если была и работала неверно — `fix`. Если не было вовсе — `feat`.

### Описание

- **Длина:** до 72 символов (весь subject — «тип(скоуп): описание»).
- **Язык:** русский (язык проекта). Технические термины на английском оставляй: `добавь debounce для resize`, `поправь CORS для /api`.
- **Точка в конце:** нет.
- **Что описывать:** смысл изменения, а не затронутые файлы.
  - Хорошо: `исправил поллинг доски после writeCode`
  - Плохо: `обновил BoardView.vue и TaskCard.vue`

## Дисциплина

**Один коммит — одна цель.** Если в голове всплывает «и ещё я заодно…» — это второй коммит.

- Баг-фикс + рефакторинг → два коммита.
- Фикс бэка + не связанный фикс фронта → два коммита.
- Правки + обновление зависимостей → два коммита (`chore` отдельно).

**Плохие сообщения запрещены:** `wip`, `fix`, `update`, `stuff`, `misc`, `temp`, `.` — такие сообщения не пропускай разработчику даже в предложенном виде.

**Не упоминай инструмент:**

- Никаких `Claude: ...`, `via Claude Code`, `generated by Claude`.
- Никаких `Co-Authored-By: Claude ...` в теле.

**Эмодзи** — только если в `git log` проекта есть устойчивая конвенция на них. По умолчанию — нет.
