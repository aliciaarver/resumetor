# API-запросы

- Токены и заголовки авторизации — через общий auth-слой/клиент проекта, не вручную в каждом компоненте.
- Ошибки API показывай пользователю понятным текстом. Не глотай.
- Состояние загрузки для любого fetch — обязательно (скелетон, спиннер, disabled-кнопка — что принято в проекте).
- URL-ы хардкодом не пишутся — через общий клиент или proxy.

## Где что живёт
- HTTP-клиент (`axios`/`fetch`-обёртка) — в одной точке проекта (`src/api/`, `src/shared/api/` — смотри соглашения). Компонент импортирует функции, а не урлы.
- Типы ответов — рядом с функциями клиента, а не в компонентах.
- Бизнес-логика запроса (кеш, ретраи, оптимистичные апдейты) — в composable/hook, не внутри шаблона компонента.

## Ошибки
- Пользователь должен увидеть, что пошло не так, и что делать дальше. Техническую деталь (`500`, stack trace) не показываем — её логируем.
- Если ошибка ломает экран — покажи fallback-состояние с кнопкой «повторить», а не пустоту.
- Сетевые ошибки (offline, timeout) отличаем от логических (validation, 4xx) — сообщение пользователю разное.
