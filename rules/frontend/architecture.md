# Архитектура компонентов

## Ответственность
- Один компонент — одна ответственность.
- Логику в шаблоне/JSX/template-слое не пиши — она должна жить в модуле компонента (setup-скрипт, hook, отдельный util).

## TypeScript обязателен
Любой фронтенд пишется на TypeScript **независимо от фреймворка** (Vue, React, Svelte, vanilla). Исключения — только легаси-код на JS, который точечно правится, и одноразовые скрипты. Новый код — всегда TS.

- `strict: true` в `tsconfig.json` (включая `noImplicitAny`, `strictNullChecks`, `strictFunctionTypes`). Ослабление флагов обсуждается отдельно и фиксируется в `TECH-LEAD.md`.
- `any` запрещён. Если тип неизвестен — `unknown` + runtime-narrowing (type guards, `zod`/`valibot` для данных извне).
- `@ts-ignore` / `@ts-expect-error` допустимы только с комментарием-причиной и желательно с тикетом на починку.
- Props / события / refs типизируй через механизмы фреймворка (`defineProps<Props>()`, `defineEmits<{...}>()`, React `FC<Props>` или явные Props-типы, `ref<HTMLElement | null>(null)`).
- Типы доменных сущностей — рядом с сущностью (в FSD: `entities/<name>/model/types.ts`). Общие утилитарные типы — в `shared/types`.

## Feature-Sliced Design (Vue / React)

Проекты на Vue и React строятся по [FSD](https://feature-sliced.design). Это обязательный скелет для новых проектов и целевой ориентир при рефакторинге существующих.

### Слои (сверху вниз)
1. **`app/`** — инициализация: провайдеры, роутер, глобальные стили, точка входа.
2. **`processes/`** _(опционально)_ — сложные межстраничные сценарии (онбординг, чекаут).
3. **`pages/`** — страницы/экраны. Композиция widgets и features под конкретный роут.
4. **`widgets/`** — крупные самодостаточные блоки интерфейса (хедер, сайдбар, канбан-борд).
5. **`features/`** — пользовательские действия с ценностью: «авторизоваться», «добавить в корзину», «переключить тему».
6. **`entities/`** — бизнес-сущности: `user`, `task`, `project`. Базовое UI сущности, её стор, типы.
7. **`shared/`** — переиспользуемый код без бизнес-смысла: UI-кит (`shared/ui`), HTTP-клиент (`shared/api`), утилиты, константы, токены.

### Правила импортов
- Импорт только **сверху вниз**: верхний слой импортирует из нижних, наоборот — нельзя.
- На одном уровне слайсы между собой **напрямую не импортируются** (фича не тянет другую фичу). Связь — через слой ниже (`entities`/`shared`) или через композицию в `pages`/`widgets`.
- У каждого слайса — **public API** (`index.ts`), наружу экспортируется только то, что явно указано. Импортировать внутренности слайса в обход `index.ts` запрещено (ESLint-плагин `@feature-sliced/eslint-config` или `@conarti/eslint-plugin-feature-sliced` — в помощь).
- Сегменты внутри слайса: `ui/`, `model/` (стор, хуки, типы), `api/`, `lib/`, `config/`. Лишние не плодим.

### Когда FSD не обязателен
- Не-Vue/React проекты — FSD как ориентир, но жёсткой обязательности нет; главное — слоистость и public API.
- Мелкий скрипт, браузерное расширение, одноразовое демо — хватит `shared/ui` + плоских страниц.
- Конкретные пути, алиасы (`@/shared`, `@/entities`) и исключения — в `TECH-LEAD.md` проекта.

## Переиспользование
- Переиспользуемую логику выноси в отдельный модуль (composable, hook, util) при использовании в 2+ местах. Не дублируй.
- Правило меры для кода такое же, как для стилей: **3+ повторений — рефакторим**, 1–2 повторения — живи с дублированием, это честнее ложной общности.
- Склеивать несвязанные места общей абстракцией только потому, что «код похож», — нельзя. Общая семантика должна быть реальной, а не случайной.

## Где что лежит
- **В FSD-проекте**: базовые UI — `shared/ui/`; хуки/composables общего назначения — `shared/lib/`; хуки фичи — `features/<name>/model/`.
- **Вне FSD**: базовые UI-компоненты — `components/ui/`, composables/hooks — в `composables/`/`hooks/`, не внутри компонентов.
- Страницы/экраны — отдельно от переиспользуемых компонентов (`pages/` в FSD, `views/`/`pages/` вне).
