# Frontend — компактные правила (универсальные)

Стек, фреймворк, палитру, test-инструменты конкретного проекта смотри в `TECH-LEAD.md` (и `FRONTEND.md`/`TESTING.md` если есть). Здесь — роль и дисциплина.

## Дисциплина компонентов
- Одна ответственность на компонент.
- Если язык поддерживает типизацию — используй её. `any` / untyped — запрещено.
- Переиспользуемую логику выноси в отдельный модуль (composable / hook / util) при 2+ точках использования.
- Логика в шаблоне/JSX — нет, вынеси в модуль.

## Стили
- Следуй токенам/палитре проекта (TECH-LEAD.md или design tokens). Не вводи новые цвета без нужды.
- Без CSS-фреймворков, если в проекте не указано иначе.
- `box-sizing: border-box`.
- **CSS, а не JS.** Если задача визуальная (truncate/ellipsis, hover, адаптив, анимации, показ/скрытие по состоянию) — решай стилями. JS не должен резать строки, слушать resize и дёргать стили. Данные в DOM не деформируй — CSS меняет вид, JS меняет данные.
- **DRY в стилях.** Значение (цвет/размер/радиус) повторяется 3+ раз → в CSS custom property (`--...` на `:root` или уровне темы), брать через `var(--...)`. Блок стилей повторяется 3+ раз → миксин (SCSS `@mixin`, Less) или класс-утилита, если препроцессора нет. Источник правды — токены из `TECH-LEAD.md`. Один-два повтора — не повод городить абстракцию.

## API-запросы
- Токены через auth-обёртку проекта, не руками.
- Ошибки API показывай пользователю осмысленно, не глотай.
- Loading-состояния для любого fetch обязательны.
- URL-ы не хардкодь — ходи через общий клиент/proxy.

## Тесты
Инструменты — из `TECH-LEAD.md` / `TESTING.md`. Обязательно для: composables/hooks/utils с логикой, критических пользовательских сценариев (auth, формы), баг-фикса (регрессионный тест). Тривиальную разметку без логики тестить не нужно. Перед сдачей тесты должны быть зелёными; отключать/скипать нельзя — фиксить.

## Перед сдачей
- Проверка типов проекта проходит без ошибок.
- Нет ошибок в консоли.
- Вёрстка переживает длинные тексты и пустые данные.
