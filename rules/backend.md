# Backend Rules (универсальные)

Правила применяются ко всем проектам, которыми управляет дашборд. Стек (язык, фреймворк, БД, HTTP-клиент, модульная система), тест-инструменты и соглашения **конкретного проекта** — в `TECH-LEAD.md` (или `BACKEND.md` / `TESTING.md`) этого проекта.

## Структура
- Каждый внешний сервис или домен — отдельный модуль (`trello.js`, `payments/`, `users/service.py` — как принято в проекте).
- Entry-файл (`server.*`, `main.*`, `app.*`) — только роуты, middleware и bootstrap. Бизнес-логика в модулях/сервисах.
- Секреты и токены — из конфигурации проекта (env, vault, заголовки), не из кода.

## API-контракты
- Все роуты возвращают единый формат ответа проекта (обычно JSON).
- Ошибка: `{ error: "описание" }` (или формат, принятый в проекте) с корректным статусом 4xx/5xx. Не возвращать 200 на ошибку.
- Успех: данные или подтверждение (`{ success: true }`) — как принято в проекте.
- Обязательные поля запроса валидируй до выполнения логики.

## Авторизация и секреты
- Токены никогда не логировать. Ни в `console.log`, ни в телах запросов к внешним API.
- Секреты не возвращать в ответах и не класть в URL.
- Авторизация — по механизму проекта (кастомные заголовки, JWT, сессии — что принято).

## Внешние API
- Таймауты на все внешние запросы — обязательно. Без них один зависший вызов положит весь роут.
- Параллельные вызовы к одному и тому же API делай аккуратно — некоторые API (особенно Trello/GitHub/YouTrack) уходят в ECONNRESET или rate-limit при параллельных запросах к одному токену. Если в проекте это зафиксировано — делай последовательно.
- Ошибки внешних сервисов пробрасывай с осмысленным сообщением, не глотай. Разработчику нужно понять, что сломалось и где.

## Тесты
Конкретные инструменты (Vitest, Jest, pytest, supertest, nock, msw, …) — в `TECH-LEAD.md` / `TESTING.md` проекта. Общее правило:

- **Обязательны** для: парсеров и чистых функций преобразования данных, роутов с нетривиальной логикой (ветвление, агрегация нескольких внешних вызовов), интеграций с внешними API (через моки — проверка что ошибки пробрасываются осмысленно), баг-фикса (регрессионный тест).
- **Не нужны** для: тонкого CRUD без логики, одноразовых admin-скриптов, очевидных обёрток.
- **Минимум** — happy path + ошибки внешних API (таймаут, 4xx, 5xx) + валидация обязательных полей.
- Токены в тестах фиктивные, никогда реальные.
- `npm test` (или команда проекта) должна проходить локально перед сдачей. Падающий тест — чинить, не скипать.

## Что не делать
- Хранить состояние в памяти процесса, если в проекте явно не предусмотрено.
- `console.log` с токенами, PII или секретами.
- `eval`, строить SQL / shell-команды конкатенацией строк.
- Отключать или пропускать падающие тесты, «чтобы собралось».
